# BUG-009 — "Only working links" verification is unreachable dead code

| Field | Value |
|---|---|
| **Bug ID** | BUG-009 |
| **Title** | "Only working links" verification is unreachable dead code |
| **Severity** | Medium |
| **Priority** | P2 |
| **Feature** | FEAT-004, FEAT-010 |
| **Environment** | commit `d24eb41`, code review of `src/app/api/chat/route.ts:110-138` |
| **Preconditions** | A custom `@handle` persona |
| **Steps to Reproduce** | 1. Read `chat/route.ts:29-31` (the leading `@` is stripped from `personaKey` before the LLM branch) and `chat/route.ts:110` (`if (personaKey.startsWith("@"))` guards the HEAD-probes) 2. Observe that the condition can never be true, so `workingLinks` is always `undefined` |
| **Expected** | As the README claims, only platforms that actually resolve are offered to the model |
| **Actual** | `workingLinks` is never populated; the ten HEAD requests never execute. `buildPrompt` therefore falls back to its own hard-coded platform list, so a persona may be told about URLs that do not exist |
| **Reproducible** | YES by inspection (dead branch) |
| **Evidence** | code references above; scenario TC-026 (the reachable code path) and TC-033 |
| **Root Cause** | The `@`-stripping added earlier in the function makes the later `startsWith("@")` check impossible; the feature was never covered by a test |
| **Fix** | Either probe links from the original `customName`/raw persona value, or remove the dead code and the README claim. If probing is kept, do it concurrently with timeouts and cache the result in the persona cookie |
| **Regression Test** | Needs provider credentials + outbound internet; documented as PLANNED in TC-012/TC-063 |
| **Status** | OPEN |
