# BUG-014 — HiPi history stores only the Hitesh reply

| Field | Value |
|---|---|
| **Bug ID** | BUG-014 |
| **Title** | HiPi history stores only the Hitesh reply |
| **Severity** | High |
| **Priority** | P1 |
| **Feature** | FEAT-002 (HiPi), FEAT-006 (history) |
| **Environment** | commit `d24eb41`, code review of `src/app/api/chat/route.ts:55-70` (runtime confirmation needs provider keys) |
| **Preconditions** | HiPi (`persona: "both"`) conversation with at least two turns |
| **Steps to Reproduce** | 1. Send a message with `persona: "both"` 2. Inspect the `chatHistory-both` cookie or the `history` field of the response 3. Send a second message and inspect the prompt context |
| **Expected** | Both persona replies are represented in the context (e.g. Hitesh and Piyush turns), so the follow-up conversation can reference both |
| **Actual** | `newHistory` appends `{role:"assistant", content: replyHitesh}` only (`route.ts:62-65`); the Piyush reply never enters the history cookie, so the Piyush half of the conversation is invisible to the next prompt (and is immediately lost for the model) |
| **Reproducible** | YES by inspection (deterministic); runtime confirmation pending credentials |
| **Evidence** | code reference `src/app/api/chat/route.ts:62-65`; TC-008 (response shape, blocked), TC-013 |
| **Root Cause** | The `both` branch builds a single assistant turn from the Hitesh reply; there is no representation for a second assistant persona in the history schema |
| **Fix** | Store both replies (e.g. one assistant turn per persona, or a combined turn) and adapt `buildPrompt`'s history serialisation to label them (`Hitesh:` / `Piyush:`) — the serialiser already supports arbitrary assistant labels |
| **Regression Test** | TC-008 + TC-013 (automated once credentials exist) |
| **Status** | OPEN |

> Note: previously tracked as a known issue; promoted to a bug because it is a code defect rather than a design
> limitation. Its former `KI-*` number is retired and intentionally not reused.
