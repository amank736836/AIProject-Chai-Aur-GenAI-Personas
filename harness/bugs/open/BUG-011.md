# BUG-011 — Whitespace-only message passes validation

| Field | Value |
|---|---|
| **Bug ID** | BUG-011 |
| **Title** | Whitespace-only message passes validation |
| **Severity** | Low |
| **Priority** | P2 |
| **Feature** | FEAT-012 |
| **Environment** | commit `d24eb41`, dev server, RUN-2026-001 |
| **Preconditions** | none |
| **Steps to Reproduce** | 1. `curl -X POST http://localhost:3000/api/chat -H 'Content-Type: application/json' -d '{"message":"   ","persona":"hitesh"}'` 2. Observe that the request reaches the provider layer instead of returning 400 |
| **Expected** | `400 {"error":"Message required"}` (a whitespace-only message is semantically empty) |
| **Actual** | `if (!message)` is a truthiness check only, so `"   "` passes and is forwarded to Groq (observed as a provider error in the credential-free environment, i.e. `500`) |
| **Reproducible** | YES |
| **Evidence** | [`../../evidence/api-responses/TC-003-chat-whitespace.json`](../../evidence/api-responses/TC-003-chat-whitespace.json) |
| **Root Cause** | `src/app/api/chat/route.ts:33` — `if (!message)`; the client-side `message.trim()` guard (`page.tsx:191`) is the only protection and is bypassable by any direct API call |
| **Fix** | Validate with `typeof message === "string" && message.trim().length > 0` (and cap the length, see TC-006) |
| **Regression Test** | TC-003 (automated, `{ todo: "BUG-011" }`) |
| **Status** | OPEN |
