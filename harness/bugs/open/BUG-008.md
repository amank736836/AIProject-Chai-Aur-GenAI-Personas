# BUG-008 — Custom-persona chat history is never read back

| Field | Value |
|---|---|
| **Bug ID** | BUG-008 |
| **Title** | Custom-persona chat history is never read back |
| **Severity** | Medium |
| **Priority** | P1 |
| **Feature** | FEAT-006, FEAT-004 |
| **Environment** | commit `d24eb41`, code review of `src/app/api/chat/route.ts:5-27` (runtime confirmation needs provider keys) |
| **Preconditions** | A custom persona conversation with at least one previous turn |
| **Steps to Reproduce** | 1. Send two messages to `persona: "test-persona"` with a valid `chatHistory-test-persona` cookie 2. Inspect the prompt (once BUG-004 is fixed) or add a temporary log 3. Compare with the built-in persona flow |
| **Expected** | Previous turns are replayed as context, exactly like built-in personas |
| **Actual** | `getHistoryFromCookies()` builds `cookieName` only when `persona === "custom"` or one of the built-ins; the client sends the **slug** (`test-persona`), so `cookieName` stays `""` and the regex `` new RegExp(`${cookieName}=([^;]+)`) `` matches the first cookie in the header. `JSON.parse(decodeURIComponent(match[1]))` then throws and is swallowed → history is always `[]` |
| **Reproducible** | YES by inspection (deterministic code path); runtime confirmation is pending provider credentials |
| **Evidence** | code reference `src/app/api/chat/route.ts:5-27`; case TC-063 |
| **Root Cause** | The server expects the literal string `custom` for the persona while the client sends the slug (`page.tsx:220`), so the read path and the write path (`chatHistory-<slug>`, line 158) disagree |
| **Fix** | Derive the cookie suffix from the request the same way the write path does (slug for custom/`@handle`, persona name for built-ins) and guard empty names before building the regex |
| **Regression Test** | TC-063 (documented FAIL; automate with credentials) |
| **Status** | OPEN |
